# AI_GUIDE — как ИИ дорабатывает план в конструкторе Workbench

Плотная памятка для ИИ (Hermes-агент, локальная или облачная модель). Цель — **править план экономно по токенам** и потом использовать его как **каркас для пошаговой сборки проекта**. Читается один раз; при правке не пересказывай эту памятку.

## 1. Что такое «план»
План проекта = граф. **Узел = шаг** (его параметры — спецификация шага). **Ребро = связь**: порядок выполнения или привязка данных. Граф хранится как один JSON (см. §3). Порядок сборки = порядок из `plan()` (§7).

## 2. Протокол правки (экономия токенов)
1. Тебе дают **бриф**: краткие правила + текущий план **минифицированным JSON**.
2. Меняй только нужное. **Не** переформатируй, **не** печатай красиво, **не** повторяй неизменные узлы прозой.
3. Верни **весь обновлённый план ОДНИМ минифицированным JSON** по схеме §3. Человек вставит его через кнопку **Импорт (↥)** или «Импорт JSON».
4. Держи `id` стабильными. Новый узел: `id = "<type>_<n>"` (n — любое свободное число). Новое ребро: `id = "e<n>"`.
5. Подними `meta.rev` на 1 — иначе холст с localStorage посчитает диск устаревшим.
6. Координаты `x/y` можно ставить любые: после импорта человек жмёт **⌗ (авто-раскладка)**. Существующим узлам `x/y` сохраняй.

## 3. Схема JSON
```
{
  "version": <n>, "name": "<строка>", "seq": <счётчик id>,
  "meta": {
    "description": "<что за план>", "workdir": "…", "stage": "plan",
    "max_parallel": 4, "log_level": "info", "input_reserve_tokens": 8000,
    "rev": <n>,                              // ↑ при каждом изменении
    "models": {                              // подключения ИИ проекта, см. §6
      "primary": { "label","provider","base_url","model","api_key_env","context_tokens","max_output_tokens" },
      "heavy":   { … то же … }
    }
  },
  "nodes": [ { "id","type","name","x","y","enabled":true,"notes":"","params":{…} } ],
  "edges": [ { "id","from":{"node","port"},"to":{"node","port"},"kind":"flow|data" } ]
}
```
`params` у узла — по схеме его типа (§5). Незаданные параметры берут значения по умолчанию.

## 4. Порты и связи (главное правило)
- Порт имеет **kind**: `flow` (порядок выполнения, сплошная линия) или `data` (данные/знания, пунктир).
- **Ребро соединяет только одинаковые kind.** `flow`→`flow`, `data`→`data`. `from` = выходной порт, `to` = входной.
- `flow`-цепочка задаёт **порядок шагов**. `data`-связь порядок НЕ задаёт — это «подключить знания/контекст/граф к шагу».
- Часть портов **динамические**: у `choice`/`direction` по одному выходу на пункт списка; у `agent` порт `graph` появляется при `graph_in:true`.
- Вход с `multi` принимает несколько рёбер.

## 5. Каталог блоков (тип · категория · in → out · ключевые params)

**Универсальные — костяк любой предметной области** (агрегаторы, анализ трафика, маркетинг, боты). У них почти нет заводских значений, только подсказки: карточка начинается пустой, заполняешь под задачу.
- `input` · flow · `in`(необязателен) → `out`,`data`(data) · kind(api/webhook/stream/feed/file/db/scrape/manual), source*, query, auth_env, schedule(once/interval/realtime/on_event), fields, dedupe_key. Может сам быть началом плана — тогда «Старт» не нужен.
- `process` · work · `in`,`kb`(data) → `out`,`data`(data) · op(filter/map/enrich/dedupe/aggregate/classify/score/join/split/clean), rule*, input_var, group_by, window
- `sink` · io · `in` → `out` · channel(api/webhook/db/file/message/email/queue/dashboard/console), target*, method, auth_env, payload, batch, rate_limit. В отличие от `output` ветка на нём не заканчивается.

Остальные блоки писались под разбор кодовых проектов; `source`, `codegraph`, `direction`, `paywall`, `expert`, `expert_group` — бери только если задача правда про анализ кода.

**Поток (flow)**
- `start` · вход конвейера · — → `out` · trigger(upload/manual/schedule/webhook/watch)
- `source` · приём проекта · `in` → `out`,`code`(data) · mode(upload/local_agent/browser/git)
- `condition` · ветвление · `in` → `true`,`false` · expression
- `loop` · цикл · `in`,`loop_back` → `body`,`done` · mode(foreach/while/repeat), max_iterations
- `queue` · очередь · `in` → `out` · mode(sequential/parallel), concurrency
- `merge` · слияние ветвей · `in`(multi) → `out` · strategy(all/any/first)
- `choice` · выбор пользователя · `in` → «порт на пункт» + `none` · options(текст: `ключ = подпись`, отступ = подпункт, `[free]/[paid]`)
- `direction` · направление анализа · `in` → «порт на подпункт» · items(текст)

**Работа (work)**
- `task` · задание · `in`,`kb`(data) → `out` · instruction
- `agent` · LLM-агент (API) · `in`,`kb`(data)[,`graph`(data)] → `out` · provider, model/model_ref, prompt
- `expert` · эксперт · `in`,`kb`(data) → `out` · role, checklist
- `expert_group` · группа экспертов · `in`,`kb`(data) → `out` · title, experts(список ролей)
- `script` · системный скрипт · `in`,`kb`(data) → `out` · runtime(powershell/bash/python/cmd/node), code

**Данные (data)**
- `kb` · база знаний · — → `data`(data) · kind(folder/files/sqlite/vector/url/api), source
- `codegraph` · граф знаний из AST · `in` → `out`,`graph`(data) · builder, source
- `context` · сборка контекста · `in`(data,multi) → `out`(data) · budget_tokens
- `transform` · преобразование данных · `in` → `out` · language(expression/python/js), code

**Выход (io)**
- `output` · результат · `in` → — · target(file/console/webhook/variable/telegram)
- `store` · хранилище · `in` → `out`,`data`(data) · writes, dataset, target
- `paywall` · гейт выдачи · `in`,`findings`(data) → `free`,`preview`,`paid`
- `progress` · экран прогресса · `in` → `out` · title
- `note` · заметка (не исполняется) · — → — · text

Полные списки параметров, значения по умолчанию и подсказки — в `js/blocks.js` (`TYPES`). Форма параметров строится из схемы автоматически.

## 6. Подключение ИИ (локальный / облачный)
Конструктор и агент используют **OpenAI-совместимый API**. Подключения проекта живут в `meta.models` (правятся в панели «AI-бриф» → «Подключение ИИ»):
- **Локальный** (Ollama / LM Studio / llama.cpp / vLLM): `base_url` вроде `http://localhost:11434/v1`, `model` — имя загруженной модели, `api_key_env` — имя переменной окружения (для локали часто фиктивный ключ).
- **Облачный**: `base_url` провайдера, `api_key_env` — **имя переменной окружения** с ключом. **Сам ключ в план не пишется никогда** — только имя переменной.
- **Hermes-агент**: тот же механизм — направь `base_url` на его OpenAI-совместимый endpoint (локальный или облачный).

**Дашборд ключей.** В панели «AI-бриф» → «Подключение ИИ» можно **вставить сам ключ** (не только имя переменной). Значение ключа хранится **локально в браузере** (`localStorage`, отдельно от плана) под именем `api_key_env` и **не попадает в план, экспорт, бриф или автосохранение**. В план всегда идёт только имя переменной.

Блок `agent`: `provider:"project"` берёт `meta.models[model_ref]` (`primary`|`heavy`); либо `provider:"openai-compatible"` со своими `base_url`/`model`/`api_key_env`. Блоки `expert`/`expert_group` выбирают модель через `model_ref`.

**Подключение по умолчанию.** Сохранённое в панели подключение ложится и в текущий план, и в общий дефолт браузера (`localStorage`, ключ `tester.models`). Новый пустой проект берёт его сразу; импорт/дубль сохраняют своё подключение, дефолт лишь добирает пустые поля. Если у плана поле пустое — при вызове подставляется дефолт.

## 6.1 Встроенный чат: проект как компактная память
У каждого проекта **свой чат** (история в `localStorage` под `tester.chat.<id>`). В модель уходит **не весь план**, а его **карта**: `id · тип · "имя" · связи`, отступ = вложенность, `+Nп` = сколько параметров у блока скрыто. Заметки и `params` в карте не показаны — на реальном плане это ~13× экономнее полного JSON.

Детали блока подтягиваются **по требованию**, одной строкой в ответе (без прозы вокруг):
- `@детали: id1,id2` — до 8 блоков: заметки, `params`, порты.
- `@ветка: id с 1` — блоки ветки **по очереди**, порциями по 8; в конце порции сказано, как запросить следующую (`@ветка: id с 9`). Максимум 3 таких запроса подряд на одно сообщение.
- `@блок: source,kb` — полная схема **типа**: назначение, порты, все параметры с допустимыми значениями и заводскими примерами.

**Два правила, без которых получается чужая карточка.**
1. **Тип выбирай по назначению, а не по созвучию имени.** В каталоге типов у каждого блока есть описание — читай его. Часть блоков заточена под разбор кодовых проектов: `source` (как код попадает в анализатор), `codegraph`, `direction`, `paywall`, `expert`, `expert_group`. Под другую предметную область бери универсальные: `start`, `task`, `agent`, `script`, `transform`, `queue`, `loop`, `condition`, `choice`, `merge`, `kb`, `context`, `output`, `store`, `progress`, `note`.
2. **Параметры нового блока задавай сам.** Незаполненные ключи получают заводские примеры из проекта анализа кода (`work\project`, `.env, *.pem`, история git) — если их не переписать, у человека останется карточка не про его задачу. Не знаешь ключей — сперва `@блок: <type>`. Конструктор после применения отдельно перечислит блоки, созданные без параметров.

Если человек назвал блок (по `id` или имени) — детали подкладываются сразу, без лишнего круга.

**Изменения из чата** возвращай списками операций, а не всем планом. Любой список можно опустить:
```json
{"add":[{"id":"a1","type":"agent","name":"Сбор данных","notes":"…","params":{}}],
 "edges":[["a1","a2"],["a2","out1"]],
 "patch":[{"id":"agent_3","notes":"…","params":{}}],
 "del":["task_7"]}
```
- `add` — **новые** блоки: `type` обязателен; `id` здесь — временное имя только для ссылок в `edges` (конструктор выдаст свой id). Координаты не указывай: после добавления схема раскладывается автоматически.
- `patch` — правка **существующих**: `id` строго из карты, поля только меняемые, `params` сливаются по ключам. Запись с неизвестным `id`, но с `type`, трактуется как создание.
- `edges` — связи `["откуда","куда"]`, порты подставятся сами; можно явно `"узел:порт"`.
- `del` — удалить блоки по id.

`meta.rev` конструктор поднимает сам. Полный план (`{nodes,edges}`) тоже принимается — он дороже и нужен только для крупной перестройки.

**Про порты при сборке.** Часть типов не встраивается в поток как попало: `start` — без входа, `output` — конец ветки (выхода нет), `kb`/`context` — только данные, `note` — без портов. В чат эти пометки приходят прямо в каталоге типов. Что не удалось применить (несуществующий тип, связь в блок без порта) — конструктор перечислит отдельным сообщением, его видно и человеку, и модели: можно прислать исправленный набор операций.

## 7. План как каркас пошаговой сборки
- `plan()` конструктора даёт **порядок шагов** по `flow`-связям — это порядок сборки. `orphans` — узлы вне потока (подключи или пропусти).
- Собирай по одному узлу в порядке шагов: `params` + `notes` узла = ТЗ на шаг; `data`-рёбра говорят, какие знания/граф/контекст питают шаг.
- Ветвления (`condition`/`choice`/`direction`/`queue`/`loop`) задают структуру управления сборкой, а не один линейный список.
- Каждый шаг маленький и проверяемый; не забегай вперёд по плану.

**Режим «Стройка»** — второй слой поверх того же графа: что из плана уже построено в коде. Он живёт отдельным файлом (`projects/<id>.build.json`) и в план не подмешивается: экспорт, история правок и бриф его не видят.
- Узел, отмеченный в стройке, запоминает **печать плана** (`spec_rev` + контракты соседей сверху). Правят план — узел «протухает» (⟳), и это расходится на шаг вниз, если сменился объявленный контракт выхода. Готово считается как «готово И не протухло», поэтому счётчик падает после правки замысла — так и задумано.
- Работу отдают наружу заданием: человек жмёт **«Выдать задание»** на блоке, конструктор кладёт срез плана вокруг этого блока (что построить, что на входе, какой контракт обязан быть на выходе, куда писать, чем проверять) на доску движка.
- Приложение с MCP забирает его инструментом **`get_task`** и отчитывается инструментом **`report_build`** (`id`, `status`, `files`, `checks`, `note`, `spec_rev`). `spec_rev` возвращай из задания **как есть**: если план успел уйти вперёд, конструктор пометит блок протухшим, а не готовым.
- Отчёт правит только стройку. Замысел меняют `patch_block`/операциями из чата — это разные вещи, и путать их нельзя.
- **Каждое сообщение моста подписано проектом.** Проектов у человека несколько, а id блоков в них совпадают (`agent_3` есть почти везде) — неподписанная правка легла бы не в ту схему. Конструктор сообщает движку, какой проект открыт; операция с чужим проектом отбивается **409** с текстом «в конструкторе сейчас открыт …». Получил такой ответ — не повторяй вслепую: перечитай `get_plan` и убедись, что работаешь с той схемой. Подпись проставляет MCP-сервер сам, из последнего `get_plan`/`get_task`; вручную её передавать не надо.

## 8. Числа
Числовые параметры настройки — с точностью **3 знака после точки** (например `temperature: 0.200`, `delay_s: 1.500`). Не округляй до целых «для простоты». Живые биржевые цены/тики — исключение.
