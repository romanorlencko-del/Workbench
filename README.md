# Workbench — блочный конструктор конвейеров

Визуальный редактор графа: собираешь конвейер из блоков, связываешь их, задаёшь
параметры — на выходе получаешь JSON-описание структуры, по которому потом
пишется исполнитель. ИИ-агент может дорабатывать план прямо из твоего редактора
кода через MCP. Без сборки и без зависимостей — только Python 3 (для `.exe` не
нужен и он).

## Установка

Три способа — подробно в [INSTALL.md](INSTALL.md):

- **Скрипты-лаунчеры** (Windows/mac/Linux): `run.bat` (двойной клик) или `./run.sh`. Нужен Python 3.8+.
- **Windows `.exe`** (один клик, без Python) — в разделе **Releases**.
- **Docker**: `docker compose up --build`.

Любой способ открывает `http://localhost:8791`. Планы сохраняются в `projects/`
рядом с приложением и переживают перезагрузку.

**Одной командой**, если Python уже есть:

```bash
py serve.py        # Windows
python3 serve.py   # macOS / Linux
```

**Офлайн-фолбэк:** двойной клик по `index.html` — работает без сервера, но
автосохранение тогда только в localStorage браузера (без диска и без ИИ-прокси).

## ИИ-агент и MCP

Workbench работает с любым OpenAI-совместимым API (облачным или локальным) и
подключается к редакторам кода (Cursor, Claude Desktop, Antigravity) через MCP.

1. **Вставь свой API.** Кнопка **✦ ИИ** → «Подключение»: укажи `base_url`, модель и
   имя env-переменной с ключом (`api_key_env`). Ключ хранится в браузере отдельно
   от плана, на диск/в экспорт не уходит — к провайдеру идёт только транзитом через
   локальный прокси (обход CORS). Дальше — чат с ИИ справа: проси менять план,
   кнопка «Применить» вносит правки.
2. **Подключи редактор кода (MCP).** Кнопка **✦ ИИ** → раздел MCP: возьми готовые
   `mcp_server.py` и конфиг, вставь в свой редактор. ИИ прямо из редактора вызывает
   инструменты правки плана (`get_plan`, `add_block`, `connect`, `patch_block`,
   `delete_block`, `layout`), изменения появляются в открытом Workbench. Движок
   (`serve.py`) должен быть запущен — мост идёт через него.

Полный каталог блоков и правила для ИИ — в [AI_GUIDE.md](AI_GUIDE.md).

## Безопасность

Слушаем только `127.0.0.1`; прокси пускает лишь сам конструктор; ключи API на диск
не пишутся. Подробно — в [SECURITY.md](SECURITY.md). Порты и биндинг настраиваются
переменными `TESTER_PORT`, `TESTER_PROXY_PORT`, `TESTER_BIND`, `TESTER_OPEN`.

## 1. Управление

| Действие | Как |
|---|---|
| Добавить блок | клик по блоку в палитре, либо перетащить его на холст |
| Связать блоки | тянуть от порта к порту |
| Создать блок «на конце связи» | тянуть от порта в пустоту → откроется быстрый список |
| Меню блоков в точке | ПКМ по пустому холсту |
| Панорама | ПКМ-тяни, средняя кнопка или пробел+тяни |
| Зум | колесо мыши · `F` — вместить всё |
| Выделить несколько | рамкой по пустому холсту, либо Shift+клик |
| Удалить / дублировать | `Del` / `Ctrl+D` |
| Отменить / вернуть | `Ctrl+Z` / `Ctrl+Shift+Z` |
| Экспорт JSON | `Ctrl+S` |
| Прогон плана | кнопка **▶ Прогон** — подсвечивает блоки в порядке выполнения |

Два типа связей:

* **сплошная** — порядок выполнения (`kind: "flow"`);
* **пунктир** — подключение знаний (`kind: "data"`), из блока «База знаний» в порт «знания»;
* **пунктирная дуга назад** — виток цикла (связь в порт `loop_back`).

## 2. Структура данных

Единственный артефакт — один JSON. Это контракт между редактором и будущим
исполнителем.

```jsonc
{
  "version": 1,
  "name": "Демо: разбор списка задач агентом",
  "meta": {
    "description": "…",
    "workdir": "C:\\…",
    "max_parallel": 4,          // глобальный потолок параллельности
    "log_level": "info",
    "input_reserve_tokens": 8000,
    "models": {                 // объявлены ОДИН раз на проект
      "primary": { "label": "Основная", "base_url": "https://api.gonka24.com/v1",
                   "model": "qwen3-235b", "api_key_env": "GONKA_API_KEY",
                   "context_tokens": 160000, "max_output_tokens": 16384 },
      "heavy":   { "label": "Тяжёлая", "base_url": "", "model": "glm-5.2",
                   "api_key_env": "GLM_API_KEY",
                   "context_tokens": 1000000, "max_output_tokens": 32768 }
    }
  },
  "nodes": [
    {
      "id": "agent_3",           // уникальный, стабильный
      "type": "agent",           // ключ из реестра блоков
      "name": "Планировщик",     // человекочитаемое имя
      "x": 310, "y": 230,        // только для холста, на выполнение не влияет
      "enabled": true,           // false = блок пропускается
      "params": { "model": "gpt-4o-mini", "temperature": 0.200, … },
      "notes": "Строит список подзадач."   // ОБЯЗАТЕЛЬНО: что блок делает.
                                           // Видно на карточке; пусто → «Проверка» подсветит
    }
  ],
  "edges": [
    {
      "id": "e_3",
      "from": { "node": "agent_3",     "port": "out" },
      "to":   { "node": "transform_4", "port": "in"  },
      "kind": "flow"             // flow | data
    }
  ],
  "seq": 40                      // счётчик для генерации id
}
```

### Правила связей

* `flow` соединяется только с `flow`, `data` только с `data` — редактор не даст иначе.
* Вход с `multi: false` держит одну связь: новая вытесняет старую.
* Любой контур **обязан** проходить через порт `loop_back` блока «Цикл».
  Контур без него — ошибка «Замкнутый контур без блока Цикл»: граф не сходится.

## 3. Каталог блоков

### Поток

| Тип | Порты (вход → выход) | Смысл |
|---|---|---|
| `start` | — → `out` | точка входа: вручную / cron / webhook / по событию файла + стартовый контекст |
| `source` | `in` → `out`, `code` (data) | как проект попадает в анализатор: `upload` (архив на сервер), `local_agent` (мини-приложение-шлюз: граф уезжает при сканировании, исходники агенты читают через него по запросу), `git` (клон репозитория). Порт `code` — единая точка доступа к исходникам: агент цепляется к нему и не знает, читается файл с нашего диска или через шлюз |
| `condition` | `in` → `true`, `false` | ветвление по выражению над `ctx` |
| `loop` | `in`, `loop_back` → `body`, `done` | `foreach` / `while` / `repeat N`, потолок витков, пауза, поведение при ошибке |
| `queue` | `in` → `out` | последовательно или параллельно ×N, FIFO/LIFO/приоритет, повторы, backoff, rate-limit, дедуп |
| `merge` | `in` (много) → `out` | свести ветви: ждать все / любую / первую |
| `choice` | `in` → **по порту на каждый вариант** + `none` | пауза: пользователь отмечает галочками, что запускать. Порты генерируются из параметра `options` (`ключ = подпись`) |

### Работа

| Тип | Порты | Смысл |
|---|---|---|
| `task` | `in`, `kb` → `out` | задание текстовой инструкцией, вход/выход переменные, таймаут |
| `agent` | `in`, `kb` → `out` | LLM по HTTP API: провайдер, base_url, модель, ключ из env, промпты, temperature, инструменты, повторы |
| `script` | `in` → `out` | системный скрипт: PowerShell / bash / python / cmd / node, cwd, env, таймаут, stdout в переменную |

### Данные

| Тип | Порты | Смысл |
|---|---|---|
| `kb` | — → `data` | база знаний: папка / файлы / SQLite / вектор / URL / API, маска, эмбеддинги, top-k, чанки, обновление |
| `codegraph` | `in` → `out`, `graph` (data) | граф знаний проекта из AST: файлы, модули, классы, функции, вызовы, импорты, модели БД, эндпоинты. Строится парсером (tree-sitter / CodeGraphContext), не LLM. Хранение Neo4j / SQLite / JSON. Агенты цепляются к порту `graph` и спрашивают его запросом |
| `transform` | `in` → `out` | пересобрать данные в контексте между шагами |

### Выход

| Тип | Порты | Смысл |
|---|---|---|
| `output` | `in` → — | файл / консоль / webhook / переменная / telegram, формат, дописывание |
| `progress` | `in` → `out` | экран хода работы у пользователя: этапы, проценты, текущий файл; отменяемость |
| `note` | — | комментарий на холсте, в выполнении не участвует |

## 4. Семантика выполнения

Так эту структуру должен читать будущий исполнитель. Ровно это и показывает
вкладка **«Очередь выполнения»**.

1. Старт — блоки `start`; если их нет, корни — узлы без входящих `flow`-связей.
2. Обычный блок: выполнить → перейти по всем исходящим `flow`-связям.
3. `condition`: вычислить `expression` над `ctx` → уйти в `true` либо `false`.
4. `loop`: на каждый виток отдать управление в `body`; связь из тела обратно в
   `loop_back` закрывает виток; когда витки кончились (или сработал
   `max_iterations`) — уйти в `done`.
5. `queue`: потомки по `out` исполняются по политике блока (порядок,
   параллельность, повторы, backoff, rate-limit) с оглядкой на `meta.max_parallel`.
6. `merge`: продолжить, когда выполнено условие `strategy`.
7. `data`-связи ничего не запускают: они лишь говорят, какие базы знаний доступны
   блоку в момент его выполнения.
8. `enabled: false` — блок пропускается, управление идёт дальше по его `flow`-выходам.

Переменные живут в общем `ctx`; блок пишет результат в `params.output_var`.
Если в разные блоки записан один и тот же `output_var`, редактор предупредит о
перезаписи.

## 5. Проверка

Вкладка **«Проверка»** (кнопка ✓ Проверить). Клик по строке подсвечивает блок.

* **ошибка** — незаполненный обязательный параметр, пустое тело цикла, контур без «Цикла»;
* **предупреждение** — нет «Старта», неподключённый вход, незамкнутый цикл, недостижимый блок, перезапись переменной;
* **инфо** — выход в никуда, неиспользуемая база знаний.

## 6. Как добавить свой тип блока

Всё в одном месте — `js/blocks.js`. Карточка на холсте, форма параметров,
проверки и план строятся из схемы сами.

```js
webhook: {
  label: 'Webhook', category: 'work', color: '#38bdf8', icon: '⇄',
  desc: 'HTTP-запрос наружу.',
  inputs:  [IN('in', 'вход', 'flow', true)],
  outputs: [OUT('out', 'дальше')],
  params: [
    { key: 'url',    label: 'URL',    type: 'text',   required: true },
    { key: 'method', label: 'Метод',  type: 'select', default: 'POST',
      options: [['GET','GET'],['POST','POST']] },
    { key: 'body',   label: 'Тело',   type: 'code', when: n => n.method === 'POST' },
  ],
  summary: p => `${p.method} ${p.url || ''}`,
}
```

Типы полей: `text`, `textarea`, `code`, `number`, `select`, `bool`, `tags`.
`required: true` — попадёт в проверку. `when: n => …` — поле показывается по условию.

## 7. Файлы

```
index.html        разметка и порядок загрузки
css/style.css     тема «пульт управления»
js/blocks.js      РЕЕСТР БЛОКОВ — здесь описывается структура
js/graph.js       модель графа, проверка, построение плана
js/editor.js      холст: отрисовка, зум, перетаскивание, связи
js/inspector.js   правая панель — форма строится из схемы

```

Числовые параметры — 3 знака после запятой (`temperature: 0.200`,
`backoff_s: 1.500`), кроме счётчиков и лимитов.

## 8. Чего здесь ещё нет

Редактор описывает конвейер, но не исполняет его: `▶ Прогон` только
проигрывает порядок шагов по холсту. Исполнитель (тот, что реально дёргает API,
запускает скрипты и держит очередь) — следующий шаг, и он должен читать
ровно тот JSON, который описан в разделе 2.
